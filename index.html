第三章 / 动手改
五步走完，配置就进去了
全程走设备自己的接口，不点网页按钮，所以页面卡死也不影响
步骤动作怎么算这一步成了
01取随机数后登录：先请求 GetRandCount.asp 拿令牌，再带 base64 密码调 login.cgi响应头里拿到 Set-Cookie 会话
02读当前配置：打开 simplewificfgAP.asp，同时取出页面里的 onttoken能读到两个频段的现行名称
03提交修改：按频段分别 POST set.cgi，一次只动一个频段，且只提交真正变化的值返回 200，且响应里没有 ErrCode
04回读核对：重新打开配置页，比对名称是否已变成新值页面回显的已经是新名称
05收尾：记下新密码，让原来的无线终端重新输入一次手机能用新密码连上

第三章 / 步骤一
先拿会话，再谈改配置
三步必须连着做完，中间停下来就会前功尽弃
# 1 取随机数 POST /asp/GetRandCount.asp Referer 必带，否则 403 # 2 登录换会话 POST /login.cgi UserName=user PassWord=base64(明文) x.X_HW_Token=<rand> # 3 会话到手 Cookie: sid=<64hex>:Language:id=1 # 4 之后所有请求都带这个 Cookie

三个容易忽略的点

会话寿命很短sid 很快失效，分进程一条条发会直接被 403 挡回
令牌每次重新取onttoken 随页面刷新重生成，拿上次的提交必然被拒
一次做完登录、读配置、提交放在同一个流程里，中途停就要重来

这三处是实测里卡最久的，逐条对一遍再提交

第三章 / 错误码解读
0x1 不是失败，先看它想说什么
同一个错误码，对应两种完全不同的原因，处理方式也不一样
情况 A

值根本没有变化

提交与当前完全相同的值也会被拒。这是设备的空写保护，说明你改的东西本来就在那儿。

自查：把新旧值摆在一起，看是不是真的一样
情况 B

参数形态不对

字段名、地址参数、频段组合，任何一处不合规都会让整张单被拒，不是只有那一个字段不生效。

自查：对着上一页那三条逐项核一遍
判断顺序：先比新旧值，再核参数形态，最后才去怀疑账号权限

第四章 / 落地
改完之后，三种用法
底层都是同一套接口，选一种顺手的就行，不必三种都用
方式入口适合什么情况
网页控制台http://127.0.0.1:8899偶尔改一次，不想记命令和参数
命令行脚本b671_set_ssid.py --ssid X --password Y批量、脚本化、交给定时任务跑
定时校正定期读一次，不一致就写回担心接入主网关后被同步覆盖

三种方式共用同一套登录与提交逻辑，改一处三处都生效。控制台默认只监听本机，要局域网访问需显式开放。

第四章 / 对账
重启之后，配置还在不在
这是改完之后最常被追问的一句，答案分两种情况
常态

正常断电重启，名称不会变回原值

写进去的是设备的持久化配置，不是内存里的临时值。重启时设备从自己的存储里读，读到的还是你改过的名称和密码。

唯一会变的场景

它接上一台真正的 FTTR 主网关

设备配置里 hilinkStart = 1、CfgMode = FTTOFTTREDGE_CT。一旦进入 FTTR 组网，无线名称和密码跟随主网关，本机改的会被覆盖。当前局域网没有这样的主网关，机制处于未触发状态。

验证方法：断电重插 → 恢复后执行 b671_set_ssid.py --check，看回读结果是否仍为设定值
